Part 1. Diagnostic Report

현재 클론앱을 Vercel에 배포하면 왜 안 될까?

치명적 충돌 3가지

현재 코드는 전통적인 로컬 상시 가동 서버 방식으로 설계되어 있어, Vercel의 무상태(Stateless) 서버리스 환경과 근본적으로 충돌합니다.

1. 백엔드(FastAPI) 미실행

루트 package.json에 프론트 빌드 스크립트만 존재하여, Vercel에 올리면 Uvicorn 백엔드는 배포조차 되지 않습니다.

API 서버 부재

2. SQLite 데이터 즉시 증발

Vercel 파일시스템은 읽기 전용(Read-only)입니다. instagram.db에 쓰기 시도시 즉시 에러가 나며, 데이터가 모두 날아갑니다.

DB 파일 쓰기 에러

3. 로컬 미디어(/uploads) 유실

사진/동영상을 로컬 폴더에 저장하는 구조여서 서버리스 인스턴스가 꺼지면 업로드된 이미지가 모두 삭제(404 에러)됩니다.

이미지 엑박 발생

⚠️ 프론트엔드 단독 배포 시에도 필요한 조치: SPA 라우팅 404

React Router(SPA) 환경이므로 vercel.json에 {"rewrites": [{"source": "/(.*)", "destination": "/index.html"}]} 설정이 없으면 새로고침(F5) 시 404가 뜹니다.

Part 2. Book Strategy

책에서 AWS EC2를 선택한 이유와 장점

책의 정석 아키텍처

🖥️ 단일 AWS EC2 + Nginx 구성이란?

AWS에서 가상 컴퓨터(EC2) 1대를 대여하고, 그 안에 Nginx(문지기)를 세워 프론트엔드와 백엔드를 한 컴퓨터 안에서 동시에 서빙하는 구조입니다.

  • 프론트엔드: npm run build로 나온 정적 파일(dist/)을 Nginx가 직접 초고속 전달
  • 백엔드: /api 요청만 EC2 내부 FastAPI(8000번 포트)로 넘겨줌
  • 스토리지/DB: EC2 영구 디스크(EBS)에 instagram.db와 uploads/가 안전하게 보존

✨ 1번 방식의 3대 핵심 이점

1. CORS 에러 원천 차단

동일 도메인/IP를 공유하므로 브라우저 보안 에러(CORS)가 0% 발생합니다.

2. 프론트/백 관리 일원화

별도 호스팅 여러 개에 가입할 필요 없이 EC2 컴퓨터 1대만 관리하면 끝납니다.

3. 무료 SSL(HTTPS) 원클릭 적용

Certbot 무료 인증서 1회 설치로 프론트/백 모두 완벽한 보안 접속 완성.

Part 3. Fact-Check

책의 설명 팩트체크: "Vercel과 웹소켓 제약"

100% 사실 입증
"서버쪽 백엔드 기능은 필요할 때만 잠깐 실행되는 서버리스 형태로만 지원되며... 특히 실시간 웹소켓(계속 연결을 유지하는 통신 방식) 연결에는 치명적인 제약이 있습니다."
- 사용자 첨부 도서 내용 중 -

❌ 안 되는 이유: Vercel 자체 웹소켓

웹소켓은 전화 통화처럼 연결(Connection)을 끊지 않고 24시간 물고 있어야 합니다. 하지만 Vercel의 서버리스 함수는 응답을 주면 즉시 종료(최대 실행시간 10~60초)되므로 Vercel 자체에 웹소켓 서버를 띄우는 것은 불가능(책 설명 100% 사실)합니다.

✅ 가능한 이유: Vercel + Supabase

Vercel에는 순수 React 화면만 올려두고, 웹소켓 연결은 24시간 켜져 있는 외부 클라우드인 Supabase와 직접 맺는 구조이기 때문에 실시간 채팅과 알림이 완벽하게 동작합니다!

Part 4. Feature Mapping

현재 FastAPI 기능은 Supabase로 충분한가?

100% 완벽 대체 가능

현재 프로젝트의 13개 라우터 로직을 전수 조사한 결과, Supabase의 무료 기능으로 모두 구현 가능하며 오히려 실시간성과 성능이 대폭 향상됩니다.

기능 영역 현재 FastAPI 구현 Supabase 대체 방식 효과
회원가입/로그인 Bcrypt 해싱 + JWT 자체 발급 supabase.auth.signUp() 구글/카카오 소셜로그인 무료 연동
피드/게시물/댓글 SQLAlchemy ORM + SQLite PostgreSQL 테이블 + RLS 보안 엔터프라이즈급 안정성 & 속도

Part 5. Advanced System

자체 추천 알고리즘 도입 시의 마이크로서비스 프로세스

머신러닝 추천 분리

🧠 "핵심 두뇌(FastAPI)와 데이터 창고(Supabase)의 역할 분담"

가벼운 잡일(로그인, 사진 저장)은 Supabase에 맡기고, CPU를 많이 쓰는 무거운 파이썬 머신러닝 연산만 FastAPI 서버에 격리시켜 전체 앱의 속도와 안정성을 지킵니다.

1

릴스 탭 클릭

철수가 스마트폰에서 릴스 탭을 누르면, 추천 서버(FastAPI)에 "철수 취향 릴스 10개만 골라줘" 요청

2

데이터 분석

FastAPI가 Supabase에서 철수의 최근 시청 이력(고양이 100% 시청, 축구 1초 이탈) 수집

3

머신러닝 연산

파이썬 머신러닝 모델이 점수를 계산하여 추천 영상 번호표(ID 10개)만 스마트폰으로 회신

4

실제 영상 재생

스마트폰이 그 번호표를 들고 Supabase 스토리지에서 고화질 영상을 CDN으로 초고속 재생

Part 6. Networking Secret

AWS 서버와 원격 DB는 어떻게 서로 연결될까?

네트워크 접속 원리

🌐 DB도 인터넷 주소를 가진 서버입니다

SQLite는 내 컴퓨터의 'USB 파일' 같지만, PostgreSQL(Supabase)은 인터넷 주소(URL)를 가진 클라우드 서비스입니다.

AWS 서버와 Supabase가 지구 반대편에 떨어져 있어도, 초고속 인터넷 보안 통신망(SSL/TLS)을 통해 0.01초 만에 안전하게 연결됩니다.

🔑 비밀은 접속 주소(DATABASE_URL) 딱 한 줄!

FastAPI 설정 파일(config.py)의 주소 한 줄만 바꾸면 즉시 연결됩니다:

# 기존 로컬 SQLite
DATABASE_URL = "sqlite:///./instagram.db"

# 원격 Supabase 클라우드 DB
DATABASE_URL = "postgresql://postgres:비밀번호@db.xxxx.supabase.co:5432/postgres"
